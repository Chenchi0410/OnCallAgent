> 适用项目：FastAPI + LangGraph（Plan-and-Execute）+ Milvus（向量库）+ MCP 工具协议 + SSE 流式接口
> 
> 使用方式：每次模拟面试后，把真实追问补充到对应问题下的「补充记录」。

## A. 最可能询问的问题（高频必问）

### 1) 你这个项目为什么说是 Agentic RAG，而不是传统 RAG？
- 面试官关注：是否理解“检索由 Agent 按需触发并迭代”的核心区别。
- 满分要点：
  - 传统 RAG 更像“固定流程：检索→拼上下文→生成”；而这里是“任务驱动：先规划，再在执行中多次工具化检索/补证”。
  - 检索能力被封装为工具，和监控/日志工具一起纳入执行链路，由 Agent 在步骤中按需调用。
  - 诊断输出包含过程（计划/步骤/证据）而不仅是一次性答案。
- 常见追问：如果检索不到/证据冲突怎么办？如何决定是否二次检索？
- 满分回答提纲（3-5句）：这个项目不是“先检索再回答”的固定 RAG 流程，而是把检索当成 Agent 的可调用能力，融入 Plan-and-Execute 的任务执行链路。Planner 会先把诊断任务拆成步骤，执行过程中 Agent 会按步骤需要去调用知识检索、日志、监控等工具获取证据，并在证据不足时触发二次检索补证。这样输出的不只是结论，还能把计划、步骤结果和引用证据一起流式呈现，可解释性和可运维性更强。遇到检索不到或证据冲突时，我们会明确缺口、再补证或降级为“排查建议”，而不是强行编造结论。

### 2) 知识库文档是怎么做 chunk 的？chunk_size/overlap 怎么定？
- 面试官关注：切分策略是否为检索效果服务，而不是“套组件”。
- 满分要点：
  - Markdown 两阶段：先按 `# / ##` 结构化切分（保留标题），再做二次长度切分，并合并过小片段避免碎片化。
  - 参数可配置：`chunk_max_size`、`chunk_overlap`，并解释 overlap 用于跨段语义连续。
  - chunk 元数据：来源文件（`_source`）、标题层级、文件名/扩展名，支持证据追溯与增量更新。
- 满分回答提纲（3-5句）：我们优先保证“语义完整 + 可追溯”，所以对 Markdown 采用两阶段切分：先按一级/二级标题切出结构化段落并保留标题，再用递归字符切分控制 chunk 大小，同时把过小片段合并回相邻 chunk，避免碎片化影响召回稳定性。chunk 的 `chunk_max_size` 和 `chunk_overlap` 是可配置的，overlap 主要解决跨段落的定义/前置条件断裂问题。每个 chunk 都会补齐 `_source`、文件名、扩展名以及标题层级等元数据，便于召回后把答案落到具体证据，并支撑后续按来源做更新。

### 3) 文档怎么入库、怎么做增量更新/全量替换？
- 面试官关注：知识库能否持续演进、不会越用越乱。
- 满分要点：
  - 索引前按 `_source` 删除旧分片，再写入新分片，实现“文件级覆盖更新”。
  - 支持目录批量索引与单文件上传索引，上传失败与索引失败解耦（文件成功、索引记录错误）。
  - 写入包含内容与元数据，便于召回后解释来源。
- 满分回答提纲（3-5句）：入库流程是“读文件→切分→向量化→写 Milvus”，并且以 `_source` 作为文件级主键实现覆盖更新：同一路径的旧 chunk 会先删除，再写入新 chunk，避免重复与脏数据累积。我们同时支持目录批量索引和单文件上传索引，便于知识库持续迭代。写入时把 chunk 内容与元数据一起存入向量库，召回后能直接回溯来源文件，保证结果可解释。即便索引失败也不会影响上传链路可用性，会记录错误用于排查与重试。

### 4) 为什么选 Milvus？还了解哪些向量库？
- 面试官关注：选型思路与约束条件（性能/成本/运维/生态）。
- 满分要点：
  - Milvus 适合高维向量检索与工程化索引（如 IVF 系列），具备成熟的社区与部署方案。
  - 对比项：Elastic/Opensearch Vector、pgvector、FAISS、Weaviate、Qdrant 等（从部署复杂度、扩展、性能、成本、生态讲）。
  - 说明你的场景：知识库规模、QPS、延迟目标、部署环境（本地/容器/云）。
- 满分回答提纲（3-5句）：我们选 Milvus 的核心原因是它在向量检索这件事上足够工程化：索引类型和参数可控，适合把知识库做成长期可维护的服务。项目里我们用统一维度的 embedding（1024 维）并建立向量索引，检索时也可以通过参数在召回率与延迟之间做权衡。对比 pgvector/ES 向量检索等方案，Milvus 在大规模向量检索的性能与索引能力上更专注；对比 FAISS 则 Milvus 更偏服务化与运维友好。最终选型还是回到约束：数据量、QPS/延迟目标、部署环境和团队运维成本。

### 5) 向量检索链路怎么评估效果？怎么做召回优化？
- 面试官关注：有没有“指标体系”和可迭代的方法。
- 满分要点：
  - 离线：召回率/命中率、MRR、nDCG、覆盖率；线上：首答可用率、人工接管率、平均诊断时长。
  - 召回优化手段：chunk 策略、top_k、embedding 模型、查询改写/扩展、混合检索（关键词+向量）。
  - 证据链：返回片段必须可追溯到 `_source`，避免“幻觉式结论”。
- 满分回答提纲（3-5句）：我们把评估分成离线和线上两层：离线用命中率、MRR/nDCG 看相关性，线上更关注首答可用率、平均诊断时长和人工接管率。优化召回不会只调 top_k，而是从 chunk 结构、embedding 模型、查询表达（改写/扩展）以及必要时的混合检索一起迭代。对运维场景来说，“可解释”也是硬指标，所以每次召回都要能回指到 `_source` 和具体片段，避免凭空下结论。最终用一套固定评测集做回归，确保每次改动可度量。

### 6) rerank 重排怎么做？为什么需要？
- 面试官关注：是否理解“向量召回≠最终相关性”。
- 满分要点：
  - 先用向量做召回（高召回、低成本），再用更强模型做重排（提升精排相关性）。
  - 技术路线：Cross-Encoder、LLM rerank、学习排序（LTR）等；权衡延迟与成本。
  - 工程：候选集大小、并发、缓存、超时与降级策略。
- 满分回答提纲（3-5句）：向量检索擅长“快而全”的召回，但排序未必符合最终问答/诊断的语义相关性，所以需要在候选集上做 rerank 把最相关证据排到前面。实现上通常是“召回 topN → 用更强但更贵的模型重排 topN”，模型可以是 cross-encoder 或 LLM 评分，甚至结合规则特征。工程上关键是控制候选集大小、并发与超时，并提供降级：重排失败就退回向量排序，保证链路可用。最后用离线指标和线上可用率共同验证重排带来的收益。

### 7) 工具调用不准确、循环轮数太多、上下文爆炸怎么治理？
- 面试官关注：Agent 上线的“可控性”。
- 满分要点：
  - 调用准确：工具契约（入参/返回约束）+ 规划/执行解耦 + 结果校验。
  - 循环控制：max_steps/max_tool_calls、重复调用检测、无新增证据则收敛输出。
  - 上下文治理：消息裁剪（保留系统提示 + 最近轮次）+ 结构化状态保存 + 长证据外部化（按需再查）。
- 满分回答提纲（3-5句）：我们把这三个问题当成“上线治理”来做：第一，工具调用准确性靠结构化规划与工具契约约束，执行阶段用 ToolNode 统一驱动工具调用，并对结果做校验与兜底。第二，循环轮数靠预算控制，比如限制最大步骤数、最大工具调用数，检测重复调用或无新增证据时强制收敛输出。第三，上下文爆炸靠消息裁剪与外部化记忆：保留必要的系统提示与最近轮次，把长证据留在检索/日志系统里按需取。这样能同时保证效果、稳定性和成本可控。

### 8) SSE 流式接口为什么要设计事件类型？前端怎么消费？
- 面试官关注：产品化交互与可观测性。
- 满分要点：
  - 合同需要：合同里面要用流式输出，可以理解，避免等待过长，不知道是卡住了还是继续加载中。 
  - 事件分层：status/plan/step_complete/report/complete/error，便于前端做进度条、步骤展示、错误提示。
  - 流式比一次性：降低等待焦虑、可随时中止、利于运维过程可解释。
  - 稳定契约：事件字段尽量向后兼容，避免前端回归。
- 满分回答提纲（3-5句）：诊断场景天然是“过程型产品”，所以我们用 SSE 把计划、步骤执行和最终报告实时推给前端，而不是让用户等一个最终答案。事件类型分层能让前端稳定消费：status 显示进度，plan 展示步骤，step_complete 展示每步证据摘要，report 给最终报告，error/complete 做收尾。这样用户能看到 Agent 在做什么、用到了哪些证据，也便于线上排查与埋点。事件结构保持向后兼容，可以避免前端因为字段变化频繁回归。

### 9) 让我针对油田真实的业务，描述一下 Plan-and-Execute 具体流程？
- 面试官关注：是否真的把 AI 技术落地到了真实的业务排障场景中，还是只会套用 LangGraph 官方 Demo。业务体感是否真实。
- 满分要点：
  - 工具边界前置（只读闭环）：我们把 Plan-and-Execute 的每一步都绑定到“四个只读工具”上（本地：`get_current_time`、`search_knowledge_base`；MCP：`get_scada_status`、`get_error_logs`）。Agent 只负责把信息取齐、诊断推演、输出现场可执行方案；任何有风险的“写操作/远程控制”都不在工具范围内，确保工业安全边界清晰。
  - Plan 阶段（规划必须结构化且可落地）：
    - 输入：告警通常包含 `device_id`（井号/设备号）、`device_type`（设备类型）、`alert_code`（告警码/规则名）、`symptom`（现象描述，可来自工人自然语言）、可选 `reported_at`（上报时间）。
    - 规划产物：Planner 不输出泛泛的“去看日志/去看指标”，而是输出带参数的步骤清单，并把“时间窗”作为第一公民。
    - 示例计划（伪 JSON，强调参数落地）：
      ```json
      [
        {
          "step": 1,
          "goal": "建立时间锚点并生成查询窗口",
          "tool": "get_current_time",
          "args": {"timezone": "Asia/Shanghai"},
          "expected": "now，并派生 time_range = [now-30m, now]"
        },
        {
          "step": 2,
          "goal": "拉取设备实时状态特征（秒级/分钟级汇总）",
          "tool": "get_scada_status",
          "args": {"device_id": "WELL-001", "metrics": ["pressure", "load", "current", "temperature"]},
          "expected": "异常指标是否越线、是否突变、是否缺失"
        },
        {
          "step": 3,
          "goal": "在同一时间窗内拉取异常日志证据",
          "tool": "get_error_logs",
          "args": {"device_id": "WELL-001", "time_range": {"start": "<now-30m>", "end": "<now>"}, "level": "ERROR"},
          "expected": "关键报错码/堆栈/通讯异常摘要（带 trace_id）"
        },
        {
          "step": 4,
          "goal": "用“现象+特征”检索 SOP/历史工单方案",
          "tool": "search_knowledge_base",
          "args": {"query": "压力突降 + 电流上升 + 日志出现通信超时", "device_type": "抽油机"},
          "expected": "返回可追溯的 SOP 片段与相似历史案例（含 _source）"
        },
        {
          "step": 5,
          "goal": "汇总输出诊断报告（结论/证据/现场操作步骤/升级条件）",
          "tool": "none"
        }
      ]
      ```
  - Execute 阶段（按步骤取证 + 结构化写回状态）：
    - Executor 通过 ToolNode 串行/受控并发地执行上面的工具调用，每完成一步就写入 `past_steps`，但**不把原始海量日志全文塞进上下文**。
    - 状态写回示例（强调“特征进状态，原文外部化”）：
      ```json
      {
        "step": 3,
        "tool": "get_error_logs",
        "evidence": {
          "error_codes": ["E_CONN_TIMEOUT"],
          "top_messages": ["gateway timeout", "scada read timeout"],
          "raw_trace_id": "log_0x7F4A"
        },
        "time_range": {"start": "2026-04-24T08:30:00+08:00", "end": "2026-04-24T09:00:00+08:00"}
      }
      ```
    - 执行过程中，Agent 会把“现象描述 + 指标异常模式 + 关键日志码”拼成检索查询串（`query`），并把 `device_type` 作为强约束透传给 `search_knowledge_base`，避免跨设备串台。
  - Replan 阶段（动态复盘的触发条件要具体）：
    - 工具失败：例如 `get_scada_status` 返回“数据缺失/通讯中断”，Replanner 会改计划：先扩大 `time_range`（如从 30m 扩到 2h），或切换为“先查日志→再用 RAG 给出保守排查步骤”。
    - 证据冲突：例如指标显示“压力正常”，但日志持续 ERROR，Replanner 会追加一步“更换指标集合（metrics）/改取网关侧日志”，并在最终结论中降低置信度。
    - 证据不足：如果日志为空但指标异常，Replanner 会要求补证（扩大窗口/提高日志级别范围），并输出“需要补哪些证据”的清单。
  - 输出阶段（让工人能拿去干活）：最终报告必须包含：
    - 结论（含置信度/不确定性说明）
    - 证据（指标摘要 + 日志 `trace_id` + SOP/_source 引用）
    - 现场可执行步骤（例如“先确认阀组状态→再检查通讯网关→最后复测指标”，按顺序、可操作）
    - 升级/停机条件（何时必须转人工专家或按安全规程处理）
- 满分回答提纲（3-5句）：我们把油田诊断的 Plan-and-Execute 落成一个“只读闭环”的证据获取流水线：Planner 先把告警拆成带参数的步骤清单，第一步用 `get_current_time(timezone)` 定准时间锚点并派生查询窗口，随后用 MCP 的 `get_scada_status(device_id, metrics)` 拉取实时指标特征，再用 `get_error_logs(device_id, time_range, level)` 在同一窗口内拿到脱敏报错证据，最后用 `search_knowledge_base(query, device_type)` 检索 SOP/历史工单进行对照验证。Executor 每完成一步都会把关键特征以结构化形式写回 `past_steps`，丢弃原始长日志避免上下文爆炸。任何一步取证失败或证据冲突都会触发 Replan：要么扩大时间窗/调整指标集合，要么降级为“补证清单 + 保守排查方案”。最终输出的是工人可直接执行的排障步骤，并附带证据引用和升级条件，做到可解释、可复盘、可落地。

## B. 可能询问的问题（中频加分项）

### 1) LangGraph 的 Plan-and-Execute 具体怎么落地？状态里存什么？
- 关注：是否理解“状态机/图执行”而非只会调用 API。
- 要点：plan（步骤列表）、past_steps（步骤结果累积）、response（最终报告）；执行完成后移除已完成步骤。
- 满分回答提纲（3-5句）：我们把诊断流程拆成两个核心节点：Planner 负责把用户目标拆成可执行步骤，Executor 负责逐步执行并把工具结果写回状态。状态里最关键的是 plan 和 past_steps：plan 是待执行步骤列表，past_steps 记录每一步的执行结果，最后由汇总节点生成 response。每执行一步就把该步骤从 plan 中移除，保证流程可收敛、可复盘。这个结构让“规划”和“工具执行”解耦，能显著提升稳定性。

### 2) MCP 工具协议在你项目里解决了什么？为什么不用直接写 SDK 调 API？
- 关注：工具生态扩展性与团队协作成本。
- 要点：工具标准化（名字+参数+返回）、多服务聚合、可替换 mock/真实实现；Agent 无需关心底层系统差异。
- 满分回答提纲（3-5句）：MCP 的价值在于把外部能力（日志、监控、工单等）统一成“可被 LLM 调用的工具接口”，工具有稳定的名字、参数和返回结构。这样 Agent 侧只关心“要什么证据”，不关心背后是 Prometheus、云监控还是自建平台，扩展新的数据源也不会改 Agent 逻辑。相比直接写 SDK，MCP 更适合团队协作与治理：可做权限、审计、mock/真实切换、灰度上线。对诊断系统来说，这种标准化工具层是可运维、可演进的关键。

### 3) 工具调用失败怎么处理？为什么要重试？重试有什么风险？
- 关注：稳定性与异常策略。
- 要点：指数退避重试、最终失败返回错误结果而不是崩溃；风险是放大下游压力，需要限制次数与超时。
- 满分回答提纲（3-5句）：工具失败在生产很常见，我们用统一的重试拦截器做指数退避重试，优先处理网络抖动或瞬时超时。重试到上限仍失败时，不让链路崩溃，而是返回结构化错误结果，提示“缺失哪类证据、下一步怎么做”。风险是重试会放大下游压力，所以要严格限制次数、总耗时和并发，并对可重试错误做分类。最终目标是“尽量拿到证据，同时保证系统稳定”。

### 4) Milvus 索引怎么选？IVF_FLAT / HNSW 等怎么取舍？
- 关注：对检索引擎的理解。
- 要点：IVF_FLAT 适合较稳妥的近似检索；关键参数 nlist/nprobe 影响召回与延迟；不同索引适配不同规模与延迟目标。
- 满分回答提纲（3-5句）：索引选择本质是“召回率、延迟、内存/成本”三者权衡。IVF_FLAT 属于更稳妥的近似检索方案，参数如 nlist/nprobe 能直接控制搜索范围：nprobe 越大召回越好但延迟更高。HNSW 在很多场景下延迟更优，但内存开销和构建成本也要考虑。我们通常会先用保守方案跑通链路，再基于线上指标与数据规模做压测和参数调优。

### 5) metric_type 选 L2/Inner Product/Cosine 有什么区别？
- 关注：embedding 归一化与距离度量。
- 要点：如果向量做过归一化，IP≈Cosine；不同 metric 会影响排序与阈值含义。
- 满分回答提纲（3-5句）：metric 的选择要和 embedding 的性质匹配：如果向量做过归一化，Inner Product 和 Cosine 在排序上等价；如果不归一化，L2 与 IP 的含义会不同。工程上最重要的是保持一致：入库和查询用同一种 metric，并在评测集上验证相关性。阈值的解释也不同，比如 L2 是“距离越小越像”，IP/Cosine 是“相似度越大越像”。一旦切换 metric，需要重新回归评估，避免线上相关性退化。

### 6) 你们怎么做可解释？如何把“结论”落到“证据”？
- 关注：诊断系统的可信度。
- 要点：chunk 元数据（来源）+ 报告里引用关键日志/指标片段 + 说明不确定性与缺口。
- 满分回答提纲（3-5句）：可解释的核心是“结论必须能回指到证据”，所以我们从数据层就把 `_source`、标题层级等元数据写入 chunk，召回后能定位到具体文件与段落。诊断报告里会引用关键日志/指标片段作为证据摘要，并把推理过程（步骤结果）保留在 past_steps 里可复盘。遇到证据不足时，我们会明确标注不确定性和缺口，并给出下一步补证建议。这样既提升可信度，也便于线上排障与复现。

### 7) Prompt 怎么设计来减少幻觉、提升工具使用意愿？
- 关注：提示词工程是否工程化。
- 要点：明确工作原则（先证据后结论）、工具优先、遇到缺证据要补证/说明；输出结构化（结论/证据/建议）。
- 满分回答提纲（3-5句）：我们把 prompt 当成“行为规范”而不是文案：明确要求先取证据再下结论，能用工具就用工具，证据不足要主动补证或说明不确定性。输出上也做结构化，至少包含结论、证据与建议，避免只给一句模糊回答。对工具使用意愿，我们会在系统提示里强调“需要实时信息请调用工具”，并把工具返回结果显式回填到后续推理里。最后用线上回放与失败样例持续迭代 prompt，而不是一次写完。

## C. 需要准备的额外细节问题（低频但一旦问到就拉开差距）

### 1) 你们怎么做端到端的效果回归与 A/B？数据集怎么构建？
- 准备方向：告警样本、历史工单、真实日志片段；离线评测 + 线上灰度。
- 满分回答提纲（3-5句）：我们会把诊断场景沉淀成可回放的数据集：告警描述、相关日志/指标片段、历史工单结论与修复动作。离线用固定评测集做回归，关注命中率、可用率和证据一致性，保证每次改动可量化。线上再通过灰度或 A/B 验证关键指标，比如首答可用率、人工接管率和平均诊断耗时。数据集持续从真实工单与线上回放中增长，形成闭环。

### 2) 多租户/权限怎么做？知识库和日志查询如何避免越权？
- 准备方向：请求级鉴权、工具层权限校验、脱敏、审计日志。
- 满分回答提纲（3-5句）：多租户的关键是把权限下沉到工具与数据层，而不是只在 Agent 文本层“提醒不要越权”。我们会在请求侧做鉴权与租户隔离，在工具层对可查询的服务/日志主题做白名单与参数校验，并对敏感字段做脱敏。所有工具调用与返回都要记录审计日志，便于事后追溯。这样即便模型产生越权意图，也会在工具层被硬拦截。

### 3) 成本/延迟怎么控？什么时候降级？
- 准备方向：候选集大小、并发、缓存、超时、fallback 到“只给排查步骤/不下结论”。
- 满分回答提纲（3-5句）：成本和延迟控制主要靠分层：召回用便宜的向量检索，昂贵的重排或大模型推理只作用在小候选集上。对工具调用和模型调用都设置超时与预算，并对幂等查询做缓存避免重复消耗。降级策略会提前定义：例如重排失败退回向量排序，日志/监控不可用时输出“排查步骤 + 需要补的证据”而不强行下结论。目标是把用户体验稳定住，同时让成本可预测。

### 4) 并发与会话隔离怎么保证？
- 准备方向：thread_id/session_id、checkpointer、请求幂等；SSE 断连重连策略。
- 满分回答提纲（3-5句）：会话隔离的核心是每个请求/会话都有稳定的 session_id（或 thread_id），并把状态与记忆绑定到这个标识上，避免串话。并发上，我们尽量让工具调用是幂等或可重试的，并为关键步骤加超时与取消能力。SSE 场景要考虑断连：前端可根据最后一个事件阶段做重连或重新发起诊断。整体目标是“多会话并发时仍可复盘、可恢复”。

### 5) 向量库数据膨胀怎么处理？如何清理与重建？
- 准备方向：按 `_source` 覆盖更新、定期重建索引、冷热分层、版本化。
- 满分回答提纲（3-5句）：数据膨胀的根因通常是重复写入或缺少生命周期管理，所以我们先用 `_source` 做覆盖更新，保证同一文件不会产生多份旧分片。长期运维上，会按版本或时间窗口做清理策略，并在必要时重建索引来恢复性能。对于高频使用与低频使用的知识，还可以做冷热分层，把低频内容放到更低成本的存储或独立 collection。所有策略的前提是可追溯与可回滚，避免一次清理造成知识缺失。

### 6) 为什么 embedding 维度是 1024？能换模型吗？
- 准备方向：与所选 embedding 模型匹配；换模型需要重建向量与索引；维度不一致要处理迁移策略。
- 满分回答提纲（3-5句）：embedding 维度是由所选模型决定的，我们在项目里统一用 1024 维是为了和 embedding 模型输出对齐，并让向量库 schema 固定化，减少工程复杂度。模型当然可以换，但换模型通常意味着向量空间变化，需要对历史 chunk 重新向量化并重建索引，否则相似度不再可比。迁移时会采用“新旧并行 + 灰度切换”的策略，确保线上效果不回退。面试时强调你理解的是“向量空间一致性”而不仅是参数大小。

### 7) 如何定位“检索没命中”还是“生成没对齐”？
- 准备方向：分层日志：召回候选、重排结果、最终引用证据；用问题切分定位瓶颈。
- 满分回答提纲（3-5句）：我们把链路拆成“召回、（可选）重排、生成”三层分别观测：先看召回候选里有没有正确证据，如果没有就是检索问题（chunk/embedding/top_k/查询表达）。如果召回有但最终答案没用上，可能是重排把它压下去了，或生成阶段没有对齐证据，需要检查引用与提示词约束。再进一步会看模型是否在缺证据时仍强行下结论，必要时强化“先证据后结论”的策略。用这种分层回放能快速定位瓶颈并给出针对性改进。

### 8) 工具返回的是 mock 数据，上线接真实系统你怎么改造？
- 准备方向：MCP server 内部替换数据源实现（Prometheus/云监控/CLS），对 Agent 接口保持不变。
- 满分回答提纲（3-5句）：我们把真实系统接入点放在 MCP server 内部，而不是改 Agent 逻辑：工具的名字、参数和返回结构保持不变，只替换数据源实现从 mock 变成真实 API/SDK。这样对 Agent 来说是无感升级，风险更可控，也便于逐个工具灰度上线。上线前会补充权限、限流、超时与审计，避免工具调用放大生产系统压力。最后通过回放真实工单验证工具数据准确性与链路稳定性。

### 11) 项目库中 Milvus 数据库存储预警工单，它的数据表结构（Schema）是怎么设计的？是纯非结构化还是混合结构化设计？
- 面试官关注：是否真的深入使用过向量数据库；是否懂得“混合检索”与“前置标量过滤（Scalar Filtering）”以避免跨设备语义串台和提升性能；怎么做到结果可溯源。
- 满分要点：
  - 核心定调：绝对不是仅仅存“一段文本+一个向量”，而是强推“结构化元数据（Metadata）+ 非结构化文本/向量”的混合架构设计。
  - Schema 字段拆解：包括主键 ID、`embedding`（核心1024维向量）、`chunk_text`（实际短文本内容），更重要的是几个强结构化的标量字段：`doc_id / _source`（链接原始长工单的溯源指针）、`device_type`（设备类型）、`alert_code`（报警类型）。
  - 为什么这么设计（杀手锏）：前置标量过滤机制。如果在诊断“油泵”时纯做语义搜索，可能因为报错文本很像而被误导去查“水泵”的方案。有了结构化字段，可以由大模型先提取意图，在 Milvus 里前置执行 `expr: "device_type == '油泵'"` 强过滤，剩下的小池子里再做倒排/向量比对计算相似度。既杜绝了由于“语义长得像”带来的跨界幻觉，又呈数量级降低了延迟。同时 `doc_id` 支撑了全量覆盖更新与溯源展示。
- 满分回答提纲（3-5句）：在我们的知识库中，Milvus 的 Schema 设计绝非单纯存储文本和向量，而是采用了“强结构化元数据 + 非结构化向量”的混合架构。除了必备的 1024 维 Embedding 和对应的 chunk 文本外，我们重点设计了 `doc_id` 原始序号、`device_type` 设备分类、`alert_code` 等结构化标量字段。这样设计的核心目的是实现“前置标量过滤（Scalar Filtering）”—— 当 Agent 确定告警来自某个特定设备时，检索会先在 Milvus 中利用 SQL 表达式过滤掉无关设备的知识，再去计算余下候选集的向量相似度；这不仅数量级提升了检索速度，更彻底杜绝了不同类型设备间因为“报错现象语义相似”而串台产生的幻觉。同时保留的原始结构化 `doc_id` 也能支撑诊断报告界面的链接透出溯源以及后期的增量覆盖更新。
- 补充记录：
  - **代码实战演示（前置标量过滤的落地）**：
    当 Agent 的 Planner 分析出当前告警设备是“抽油机”后，在调用检索工具时，会在原生 Milvus 或 LangChain 的查询中传入布尔条件 `expr`：
    ```python
    # 假设使用 Pymilvus 或 LangChain 的 VectorStore 检索
    results = vector_db.similarity_search(
        query="管子扑哧扑哧响、不带压", 
        k=5,
        # 这就是传说中的前置标量过滤（类似 SQL 的 Where 条件）
        expr="device_type == '抽油机' and alert_code != '0x0000'"
    )
    ```
    **底层原理解释**：Milvus 引擎收到指令后，不会立刻去做耗时的 1024 维向量比对找“扑哧扑哧响”。它会先使用类似 SQL 倒排扫描的方式，跑 `expr` 规则，把不是“抽油机”的那 8 万条别的设备工单瞬间 Pass 掉（标量过滤极快）。然后再对仅剩下的 1000 条抽油机相关经验执行 KNN 向量余弦距离计算。这就是工业界典型的“混合检索”防幻觉落地姿势。

## E. 行业认知探讨与架构视野拓展

### 1) 探讨题：怎么看待现在的 RAG 演进？像 Karpathy 提倡用 Obsidian 做知识库存 Markdown/代码就能满足检索，大模型长上下文时代，向量数据库还有没有需求？
- 面试官关注：是否盲从架构（跟风上向量库），有没有深度的技术降级思维和对前沿趋势（Long Context）的敏锐度。
- 满分要点：
  - 承认局限：向量检索（Dense Retrieval）本质是算“语义模糊相似度”，对于代码变量名、错误码、特定术语这种需要“精准精确匹配”的场景，传统倒排索引（BM25）或纯 Markdown 文本搜索反而效果更好（这就是 Karpathy 观点的核心）。
  - 拆解大模型长上下文（Long Context）冲击：大模型现在支持 1M/2M token，导致“切碎知识（Chunking）然后拼凑”的传统 RAG 劣势凸显（丢失了文档的上下文结构）。直接把整篇 Markdown 丢给模型往往逻辑更连贯。
  - 向量数据库的真实需求（油田场景）：依然需要。第一，海量历史工单和非结构化 SOP 远超百万 token，无法一次性塞入 prompt；第二，需要解决“语义鸿沟”，比如一线工人口语报修“油管不出油、扑哧扑哧响”，需要通过向量语义搜索映射到标准故障库“抽油机气锁”。
- 满分回答提纲（3-5句）：Karpathy 提倡的纯文本检索非常精准，这切中了单纯向量 RAG 的痛点——向量擅长语义模糊匹配，却极容易在搜索特定代码、日志 ID 或专业词汇时丢失精度。加上现在大模型长上下文能力极强，直接检索整篇 Markdown 扔给大模型，往往比切碎成 chunk 效果更好。但这不意味着向量数据库被淘汰，现在的最佳实践是“混合检索（Hybrid Search，即 BM25精确匹配 + 向量语义匹配）”。在我们的油田场景中，当一线工人用口语化描述“管子不抽油有响声”时，精确匹配会失效，依然需要向量数据库的语义映射能力将其关联到标准的“提捞采油故障 SOP”；只是我们不再单纯依赖向量，而是将其作为复杂诊断链路中的一个召回分支。

### 2) 探讨题：近期 Claude Code (CC) 源码展示了其独特的上下文压缩与记忆管理方式，你怎么看待它的上下文压缩策略？能够给 Agent 架构带来什么启发？
- 面试官关注：是否对业界最前沿（SOTA）的 Agent 架构有持续跟进？是否真正理解“长上下文窗口（Long Context）≠ 毫无节制地塞数据”，懂得精细化的状态机内存管理与底层缓存机制（Prompt Caching）。
- 满分要点：
  - 点破 CC 压缩策略的本质特征：动态剪枝（抛弃庞大的中间工具执行 raw data，只留结果）、分层/树状记忆（当前高优先级工作区 vs 已压缩的历史快照），以及为了极致利用底层大模型 Prompt Caching 而保持上下文头部的相对静态。
  - 结合大模型痛点（Lost in the Middle）：无限堆叠上下文会导致 Attention 注意力稀释，大模型极容易出现“幻觉”或漏掉关键指令，且 Token 推理成本极其高昂。
  - 投射到大港油田项目（核心升华）：在 Plan-and-Execute 架构中，引入类似的“阅后即提取/压缩”逻辑。当 Executor 从 MCP 防腐层拿到长达上万行的通信日志后，不仅要丢弃原始废数据，更是只把提取出的诊断核心特征写入 LangGraph 的 `past_steps` 状态字典中，轻装上阵。
- 满分回答提纲（3-5句）：Claude Code 揭示了当前顶尖 Agent 的最佳实践并非单纯依赖模型的长上下文窗口，而是采用了“动态提取 + 记忆剪枝”的精细化策略，并且利用保持历史上下文不可变来极大化命中 Prompt Cache（提示词缓存）。这给我们在设计油田智能体时带来了根本性的架构启发：在真实排障中，如果把调取的全量 SCADA 时序日志无限追加到对话链路里，必然会导致大模型产生“中间失忆（Lost in the Middle）”和 Token 爆炸。因此我们吸取了 CC 的“阅后即压缩”机制：由 LangGraph 的 Executor 在拿到海量底层数据后，必须做一次前置清洗和特征提取，只把“明确的报错堆栈、异常指标”等摘要信息保留在当前的状态流（past_steps）里去指导下一步动作。这种设计不仅一锤定音解决了幻觉，还在高并发调用下省下了巨额的模型成本。

### 3) 追问：具体落地中，如何区分上下文中哪些该保留、哪些该删除？保留的格式是什么样的？
- 面试官关注：考察候选人是否有真实的大规模数据处理经验，状态机（StateGraph）内存管理的细腻度，以及数据抽象与结构设计能力。单纯回答 `{处理完毕}` 会让面试官觉得丢失了“诊断证据”，无法支撑最终的排障报告。
- 满分要点：
  - 核心准则（特征进上下文，原始数据留在外存）：判断保留与删除的唯一标准，是“该数据是否必须作为下一步推理的显式条件”或“最终诊断报告的核心证据”。
  - 坚决删除（Drop）：工具返回的原始长文本（如 5000 行未过滤的 SCADA 报文）、全量 HTTP 响应体、死循环或无效重试中的冗余思考过程（只保留最终失败事实）。
  - 必须保留（Keep）：提取出的“业务特征（Features）”、触发告警的具体阈值、步骤结论，以及指向原始数据的“关联指针（Trace ID 追踪符）”。
  - 保留的格式（Format）：在 LangGraph 状态机中不能用含糊的泛文本，而应采用高密度的结构化 JSON（K-V键值对）存入 `past_steps` 字典。
- 满分回答提纲（3-5句）：区分删留的唯一准则，是看这段数据是否作为“下一步推理的直接条件”或“最终报告的核心证据”。在真实的油田链路中，我们会果断删掉（截断）通过 MCP 查回来的那几千行原始通信日志或全量 SCADA Json 树；而保留下来的，是通过大模型或正则前置清洗出的“特征数据”。在 LangGraph 的状态中，我们保留的绝不是一句模糊的“告警已处理”，而是高密度的结构化 JSON，例如 `{"step": "查询采油树压力", "evidence": "瞬时压力突降至 2.1MPa，低于预警线", "raw_trace_id": "log_0x7F4A"}`。这种“特征浓缩 + 原始指针”的格式，既能让大模型接下来的推理在干净的截面里“轻装上阵”，又确保了最终出具排障报告时有确凿的数据支撑，绝不会出现事实幻觉。

### 4) 面试核心挑战：如何全面评估一个 Agent 系统的效果？有哪些核心指标和具体的评估方法？
- 面试官关注：是否只停留在“跑几个 Case 凭肉眼看结果好不好”的玩具开发阶段，有没有构建工程化的、多维度的自动化评测体系（Eval）。因为评估 Agent 比评估单一的 LLM 生成要难得多（涉及多步工具调用和环境状态流转）。
- 满分要点：
  - 评估维度必须拆分：不能只看最终输出，必须分“最终业务结果”、“过程轨迹（Trajectory）”和“合规可信度”。
  - 核心指标（Metrics）：
    1. 业务结果指标：排障任务闭环率（Task Success Rate）、人工接管率（Human Takeover Rate）。
    2. 过程轨迹指标：工具调用准确率（Tool Selection & Params Accuracy，选错工具或传错参数的比例）、合理执行步数（衡量是否绕弯路/死循环）。
    3. 可信指标：幻觉率、证据引用命中率（结论是否有明确的底层数据 / Trace ID 支撑）。
  - 评估方法（Methods）：
    1. 离线回放（Offline Replay base on Golden Dataset）：沉淀历史经典工单组建基准测试集。
    2. 规则断言 + LLM-as-a-Judge：绝对事务（工具、参数）用代码判死，逻辑论述交由更强调度模型打分。
    3. 线上影子模式（Shadow Mode）：线上并行但不发声，对比真人老专家的处理方式差异，并收集采油工人的显式反馈（点赞/踩）。
- 满分回答提纲（3-5句）：评估 Agent 不能像传统大模型那样只看最后生成的文字，因为它是多步交互的；我们将指标拆分成了“结果、过程、可信度”三层。在指标体系上，除了看业务维度的“排障闭环率”和“人工接管率”，我们更死盯执行过程的“MCP 工具调用准确率（有没有调错工具或传错参数）”以及衡量是否死循环的“平均决策步数”。在具体评估方法上，我们抽取了油田历史上几百份经典的排障工单与标准 SOP 作为离线基准测试集（Golden Dataset）；每次链路发版都会跑自动化回放，其中“是不是调了对应的 SCADA 数据工具”用强规则代码断言匹配，而最终的“诊断依据是否充分”则使用 LLM-as-a-Judge（让更强模型打分），辅以线上的影子模式对比真人专家的处置动作，真正把 Agent 的评测做到了工程化闭环。

## D. 核心亮点：为什么从 Function Call 升级到 MCP 协议？（油田特色绝杀题）

**1. 核心定调：MCP 是一套“带隔离墙的分布式的 Function Call”**
- **以前（普通 Function Call）**：紧耦合。每次调甲方接口，大模型后端代码全在处理油田老系统的脏数据，甚至要在 Agent 逻辑里去写复杂的 HTTP 请求构造与解析。
- **现在（MCP 方案）**：MCP 充当了 Agent 与异构数据源之间的“防腐层（Anti-Corruption Layer）”和“安全隔离墙”。HTTP 请求全部下沉在独立的 MCP Server 里，Agent 只下发标准指令。

**2. 落地四大细节（油田排障特色）**
- **数据脱敏与安全控制**：MCP Server 作为中间代理，不仅封装了 HTTP 链接，更重要的是在 Server 内部做了数据的“精简与脱敏”，确保原始涉密 JSON 字段（如坐标、产量）绝对不会暴露并外发给 LLM。
- **OT/IT 语义字典（防幻觉）**：老旧接口返回的可能是“0x7F4A”这样的机器机器码，MCP 在内部做了一层 Mapping，转换成“抽油机皮带断裂告警”的自然语言再喂给 LLM，扫平了模型理解专业壁垒。
- **结果预聚合与裁剪（防 Token 爆炸）**：大量原始日志直接返回会撑爆上下文。MCP 在读取接口后进行截断（Truncate）或降采样（Down-sample），把上万条心跳日志浓缩为统计特征后再传给模型。
- **弱网重试兜底（保执行流）**：隔离了底层老旧 API 的网络抖动。当老系统 502 时，MCP 完成内部重试；即便最终失败也会输出人类可读的结构化错误，保证了 LangGraph 的 Plan-and-Execute 状态机不会因为单次网络崩溃而整个中断。
