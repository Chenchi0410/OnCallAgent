# MySQL 面试八股（速答版）

> 结构：一句话结论 → 关键机制/公式 → 常见追问 → 易错点/实战建议。

## 1) 索引：B+Tree、聚簇/非聚簇、最左匹配

### 一句话回答
InnoDB 默认用 **B+Tree** 做索引；**聚簇索引（clustered）** 的叶子节点存整行数据（按主键组织），**二级索引（非聚簇）** 的叶子节点存「二级索引键 + 主键值」，回表再按主键取整行；联合索引遵循 **最左前缀匹配**。

### 关键点（能展开就加分）
- **为什么是 B+Tree**：范围查询友好；叶子节点有序且链表连接，顺序扫描成本低；树高小、I/O 少。
- **回表（Back to Table）**：二级索引命中后，还需要拿主键再走聚簇索引取其他列。
- **覆盖索引**：查询列都在索引里，就不需要回表（性能常显著提升）。

### 最左匹配怎么说清楚
- 联合索引 `(a, b, c)`：
  - 能用：`a`、`a,b`、`a,b,c`，以及 `a` 的范围后只能用到 `a`（后续列一般无法继续用于精确定位）。
  - 例：`where a=1 and b=2` ✅；`where b=2` ❌（通常无法利用该联合索引的有序性）。

### 常见追问
- **`like '%xxx'` 为什么不走索引？** 前缀不确定，无法利用有序性（除非改为 `xxx%` 或用倒排/全文/生成列等策略）。
- **什么时候建联合索引 vs 单列索引？** 高频组合过滤/排序/分组优先联合；遵循“选择性高的列靠前 + 贴合 where/order by/group by”。
- **Explain 里 `type` 从好到差？** 大体：`const`/`eq_ref`/`ref` > `range` > `index` > `ALL`。

## 2) 事务：ACID、隔离级别、MVCC

### 一句话回答
事务保证 **ACID**；InnoDB 通过 **redo/undo + MVCC + 锁** 实现原子性/持久性/一致性/隔离性；隔离级别从低到高是：读未提交、读已提交、可重复读、串行化。

### ACID 怎么落到实现（别只背概念）
- **A 原子性**：undo log 支持回滚。
- **C 一致性**：由约束 + 应用逻辑 + 事务隔离共同保证（不是某一个组件“自动保证”。）
- **I 隔离性**：MVCC（快照读）+ 锁（当前读）+ 隔离级别。
- **D 持久性**：redo log（崩溃恢复）+ 刷盘策略。

### 4 隔离级别与典型现象
- 读未提交（RU）：可能脏读。
- 读已提交（RC）：避免脏读，仍可能不可重复读、幻读（部分场景）。
- 可重复读（RR，InnoDB 默认）：快照读避免不可重复读；配合 next-key lock 在当前读下抑制幻读。
- 串行化（SER）：强隔离，性能最差。

### MVCC 的一句话解释
MVCC 通过 **undo 版本链 + Read View** 提供一致性读（快照读），读不阻塞写、写不阻塞读（在快照读场景）。

### 常见追问（高频）
- **“MVCC 是无锁读写”准确吗？**
  - 更准确：快照读通常不加锁；但 `select ... for update`/`lock in share mode` 属于当前读，会加锁。
- **RR 下为什么还能幻读？**
  - 快照读看到的是一致性视图；当前读（更新/加锁读）需要靠 next-key lock 防幻读。

## 3) 锁：行锁 / 表锁 / 间隙锁（防幻读）

### 一句话回答
InnoDB 主要用 **行级锁**；为了解决范围查询的“插入幻影”，会在 RR 下对索引范围加 **next-key lock（记录锁 + 间隙锁）**，从而防止其他事务在间隙插入导致幻读。

### 你需要能说清的 3 类锁
- **表锁**：锁粒度大，冲突多（某些 DDL/显式表锁）。
- **行锁（Record Lock）**：锁住具体索引记录（注意：InnoDB 行锁是“锁索引记录”，不是锁物理行）。
- **间隙锁（Gap Lock）**：锁住索引记录之间的区间，阻止插入。
- **Next-key lock**：Record + Gap 的组合，常用于范围条件。

### 易错点（面试很爱问）
- **没有用到索引的更新会怎样？** 可能导致锁范围变大（甚至退化成更大范围的锁/扫描），并发急剧下降。
- **唯一索引等值查询** 通常锁更精确；**范围查询/非唯一** 更容易触发 next-key。

## 4) 优化：加索引、优化 SQL、减少关联、用缓存

### 一句话回答
优化优先级通常是：先定位瓶颈（慢查询/执行计划/指标）→ 让查询“少扫 + 少回表 + 少排序/临时表”→ 再考虑架构层（缓存、读写分离、分库分表）。

### SQL 优化常用抓手（可按场景答）
- **索引**：
  - where 过滤列建索引；order by/group by 尝试利用索引有序性；尽量覆盖索引减少回表。
- **避免导致索引失效的写法**（常见）：
  - 对索引列做函数/隐式类型转换；`like '%x'`；`or`（可改 union）；不合理的范围条件。
- **减少关联**：能先过滤再 join；避免大表无条件 join；只取需要列。
- **排序/分组**：警惕 `Using filesort`、`Using temporary`；尝试通过联合索引支持排序/分组。

### 缓存怎么答更像“做过项目”
- **读多写少**：优先缓存热点 key（列表/详情）；设置 TTL + 失效策略。
- **一致性**：常用“先更新 DB，再删缓存（或延迟双删）”，避免强依赖缓存一致。
- **防击穿/穿透/雪崩**：互斥锁/逻辑过期/布隆过滤器/随机 TTL。

## 5) 死锁：四大条件、超时/检测/回滚

### 一句话回答
死锁满足四条件：互斥、占有且等待、不可抢占、循环等待；InnoDB 通过 **死锁检测** 或 **锁等待超时** 处理，通常回滚代价更小的事务并返回错误，需要应用层重试。

### 你要能说的落地措施
- 固定加锁顺序（按主键/业务一致顺序更新）。
- 缩短事务、减少锁持有时间（别在事务里做慢 IO/外部调用）。
- 用索引让锁更精确（避免扩大锁范围）。
- 捕获死锁错误（如 `Deadlock found when trying to get lock`）并做有限重试。

## 6) 常考补充（建议你简历/项目里也能兜住）

### 6.1 InnoDB vs MyISAM（经典）
- InnoDB：支持事务、行锁、外键、崩溃恢复（主流）。
- MyISAM：不支持事务、表锁为主，适合历史/只读但现在较少用。

### 6.2 三大日志：redo / undo / binlog
- **redo log**：物理/页级的重做，用于崩溃恢复（InnoDB）。
- **undo log**：逻辑回滚 + MVCC 版本链。
- **binlog**：逻辑变更日志（MySQL Server 层），用于主从复制/点时间恢复。
- 常见追问：**两阶段提交（2PC）** 保证 redo 与 binlog 一致性（事务提交时）。

### 6.3 Explain 你至少要会看哪些字段
- `type`、`possible_keys`、`key`、`rows`、`Extra`。
- Extra 常见：`Using index`（覆盖索引）、`Using where`、`Using filesort`、`Using temporary`。

### 6.4 主从复制与读写分离（如果项目用过）
- 异步/半同步复制；可能有延迟。
- 读写分离要处理“读到旧数据”：读主、延迟判断、业务降级。

### 6.5 分页优化（高频实战题）
- 深分页 `limit offset, size` 会越翻越慢。
- 常用：基于“游标/主键”的 `where id > last_id limit size`。

- “我排查慢 SQL 一般先看 `explain` 和慢查询日志，确认是扫表、回表还是排序/临时表，然后针对性做联合索引或改写 SQL。”
- “并发问题我会先确认是快照读还是当前读，再结合隔离级别判断是否会触发 next-key lock 或死锁。”
