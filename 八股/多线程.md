# 多线程 / 并发（Java）面试八股（速答版）

> 结构：一句话结论 → 关键机制 → 常见追问 → 易错点/实战建议。

---

## 1) 线程生命周期：新建 → 就绪 → 运行 → 阻塞/等待 → 终止

### 一句话回答
Java 线程从创建到结束会在“可运行/运行/阻塞/等待/终止”等状态间切换；状态切换由调度器 + 锁/IO/条件等待共同决定。

### Java 的 Thread.State（更准确的口径）
- `NEW`：新建未启动
- `RUNNABLE`：可运行（含就绪/运行，Java 不区分 ready/running）
- `BLOCKED`：等待进入 `synchronized` 监视器（竞争内置锁）
- `WAITING`：无限期等待（`Object.wait()` / `Thread.join()` / `LockSupport.park()`）
- `TIMED_WAITING`：超时等待（`sleep`/`wait(timeout)`/`join(timeout)`/`parkNanos`）
- `TERMINATED`：终止

### 常见追问
- **`sleep` 会释放锁吗？** 不会。
- **`wait` 会释放锁吗？** 会（释放对象监视器锁），但必须在持有该锁的 synchronized 块里调用。

## 2) 线程池：7 参数 + 4 种拒绝策略

### 一句话回答
线程池用“核心线程数 + 最大线程数 + 队列 + 拒绝策略”等参数来平衡吞吐与资源，避免无限创建线程导致 OOM/频繁上下文切换。

### ThreadPoolExecutor 7 个核心参数
1. `corePoolSize`：核心线程数
2. `maximumPoolSize`：最大线程数
3. `keepAliveTime`：非核心线程空闲存活时间
4. `unit`：时间单位
5. `workQueue`：任务队列（`ArrayBlockingQueue`/`LinkedBlockingQueue`/`SynchronousQueue` 等）
6. `threadFactory`：线程工厂（命名、优先级、是否 daemon）
7. `handler`：拒绝策略（饱和时处理新任务）

### 线程池处理任务的典型流程（背这个能接住追问）
1. 线程数 < core：创建核心线程执行
2. 否则入队列
3. 队列满且线程数 < max：创建非核心线程执行
4. 队列满且线程数 = max：触发拒绝策略

### 4 种常见拒绝策略
- `AbortPolicy`：直接抛异常（默认）
- `CallerRunsPolicy`：调用方线程自己执行（背压，常用）
- `DiscardPolicy`：直接丢弃
- `DiscardOldestPolicy`：丢弃队列最旧任务，再尝试提交

### 常见追问（加分）
- **队列选型影响很大**：
  - 有界队列：更可控，能形成背压；
  - 无界队列（如默认 `LinkedBlockingQueue`）：可能导致任务堆积、内存压力大；
  - `SynchronousQueue`：不存任务，提交即交付线程，常用于高弹性（如缓存线程池）。
- **怎么配置线程数？**
  - CPU 密集：接近 CPU 核数（或 +1）
  - IO 密集：可适当大于核数（用压测/监控决定）

### 示例代码（常用写法）
```java
ExecutorService pool = new ThreadPoolExecutor(
    8,
    16,
    60L,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    r -> {
        Thread t = new Thread(r);
        t.setName("biz-pool-" + t.getId());
        return t;
    },
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

## 3) synchronized（自动锁） vs Lock（手动锁）

### 一句话回答
`synchronized` 是 JVM 层面的内置锁，语法简单、异常安全（自动释放）；`Lock`（如 `ReentrantLock`）是显式锁，功能更丰富（可中断、可超时、公平锁、多个 Condition）。

### 对比要点
- `synchronized`
  - 自动加解锁（退出代码块/异常都会释放）
  - 基于对象监视器（monitor）
  - wait/notify 配合使用
- `Lock`
  - 必须手动 `lock()/unlock()`（通常放 finally）
  - 支持：`tryLock()`、`lockInterruptibly()`、公平锁
  - `Condition` 支持多个条件队列（比 wait/notify 更灵活）

### Lock 示例（异常安全写法）
```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // critical section
} finally {
    lock.unlock();
}
```

## 4) volatile：保可见 / 禁重排，不保原子

### 一句话回答
`volatile` 保证**可见性**和**有序性**（通过内存屏障限制重排），但不保证复合操作的原子性（如 `i++`）。

### 常见追问
- **`volatile` 为什么不保证原子？**
  - `i++` 是读-改-写三步，即使每步可见也可能并发覆盖。
- **什么场景适合 volatile？**
  - 状态标记（停止线程）、单例双重检查（配合正确实现）、发布-订阅式的轻量状态同步。

### 经典例子：停止线程
```java
class Worker implements Runnable {
    private volatile boolean running = true;
    public void stop() { running = false; }
    public void run() {
        while (running) {
            // do work
        }
    }
}
```

## 5) CAS：无锁原子更新；ABA 用版本号解决

### 一句话回答
CAS（Compare-And-Swap）通过“比较旧值是否等于期望值，等于则更新”为基础实现无锁原子更新；问题在于自旋开销与 ABA，ABA 可用版本号/时间戳（如 `AtomicStampedReference`）解决。

### CAS 伪代码
```text
function cas(addr, expected, update):
    if *addr == expected:
        *addr = update
        return true
    else:
        return false
```

### Java 示例：AtomicInteger
```java
AtomicInteger ai = new AtomicInteger(0);
ai.incrementAndGet(); // 内部 CAS 自旋
```

### ABA 怎么讲清楚（面试高频）
- 线程 T1 读到 A
- 线程 T2 把 A 改成 B，又改回 A
- T1 CAS 发现还是 A，误以为没变
- 解决：带版本号（A@1 -> A@2），或用更高层的锁/队列结构规避。

## 6) 常考补充（建议至少掌握这些“救命题”）

### 6.1 JMM 与 happens-before（回答更专业）
- JMM 关注的是“线程间如何通过内存交互”。
- happens-before 规则（常背 3~5 条就够）：
  - 程序次序规则（单线程内顺序）
  - 监视器锁规则（unlock happens-before 后续 lock）
  - volatile 规则（写 volatile happens-before 读 volatile）
  - 线程启动/终止规则（start/join）

### 6.2 AQS（ReentrantLock/CountDownLatch/Semaphore 的底座）
- AQS 用一个 state + FIFO 等待队列实现可重入锁/共享锁等同步器。
- 面试答法：Lock 的阻塞/唤醒是基于 `LockSupport.park/unpark`，队列由 AQS 管理。

### 6.3 wait/notify vs Condition
- `wait/notify`：依附于对象监视器，只有一个等待队列。
- `Condition`：一个锁可以创建多个条件队列（更精细的唤醒）。

### 6.4 死锁：四条件 + 排查
- 四条件：互斥、占有且等待、不可抢占、循环等待。
- 排查：`jstack` 看线程栈与锁依赖；线上配合监控/超时与降级。
- 规避：固定加锁顺序、缩小锁范围、减少嵌套锁。

### 6.5 并发容器（常问“为什么 HashMap 不行”）
- `HashMap` 线程不安全；并发场景用：
  - `ConcurrentHashMap`（分段/桶级并发 + CAS + synchronized 细粒度）
  - 阻塞队列：`ArrayBlockingQueue`/`LinkedBlockingQueue`

### 6.6 ThreadLocal（线程变量）
- 用于线程内传递上下文（traceId、用户信息），注意：线程池下要清理，避免复用导致脏数据/内存泄漏。

## 7) 面试“并发问题排查”串讲模板（背这个很顶用）

当被问“线上并发问题你怎么定位”：
1. 先判断现象：CPU 飙高（自旋/死循环）还是线程阻塞（锁竞争/IO）还是吞吐下降（队列堆积）。
2. 看线程池指标：活跃线程数、队列长度、拒绝次数。
3. 看线程栈：`jstack` 是否大量 BLOCKED/WAITING，是否死锁。
4. 对症下药：优化锁粒度、减少临界区、引入无锁结构/并发容器、合理拆分线程池与队列。

- “我一般用线程池隔离不同业务，拒绝策略用 CallerRuns 做背压，避免把系统打挂。”
